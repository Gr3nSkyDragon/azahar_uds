Azahar UDS Real - retail association ordering fix
=================================================

Changed source file
-------------------
src/core/hle/service/nwm/uds_real/nl80211_monitor.cpp

What this fixes
---------------
The monitor worker previously transmitted replies generated while processing a
captured packet before it handled the AP station operation generated by that
same packet.  For a retail association request, that produced this order:

  1. association response transmitted
  2. retail station registered
  3. CCMP pairwise key installed and station authorized

The retail 3DS could therefore proceed immediately after the association
response while the kernel AP still had no usable station/key state.  The new
worker order handles pending AP station operations first, then transmits queued
frames on the next iteration.

Installation
------------
Extract this ZIP into the root of your Azahar source checkout.  The included
src directory must merge with the existing src directory.  Confirm that this
file is replaced:

  src\core\hle\service\nwm\uds_real\nl80211_monitor.cpp

No CMake regeneration is required because this patch adds no source files and
does not change CMakeLists.txt.  Open the existing generated solution/project
in Visual Studio and build the same Release x64 target as before.

Expected log order
------------------
At association time, the important messages should now appear in this order:

  UDS Real: observed physical association request ...
  UDS Real AP: retail station registered and authorized ...
  UDS Real: physical TX ..., type=0, subtype=1 ...

The station-registration line must precede the association-response TX line.
Please retain the full Azahar log even if the trade still fails; the next key
question is whether protected type=2 frames arrive from the retail 3DS after
this corrected association sequence.
